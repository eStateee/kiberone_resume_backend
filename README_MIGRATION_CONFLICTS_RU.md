# Разрешение конфликтов миграций Django (рассинхронизация миграций)

Это руководство объясняет, как разрешить конфликты миграций на сервере, если ранее на нем выполнялась команда `makemigrations` непосредственно в рабочей базе данных.

В Django история миграций должна представлять собой единую линейную цепочку файлов. Если в локальной версии и на сервере были сгенерированы разные миграции (что привело к появлению "multiple migration heads" — нескольких параллельных ветвей миграций), простое копирование новых файлов локальных миграций на сервер вызовет ошибку:
`django.db.migrations.exceptions.AmbiguityError: app_resumes has more than one migration head.`

Чтобы безопасно разрешить этот конфликт без потери данных на сервере, выполните последовательность шагов, описанную ниже.

---

## 🔍 Шаг 1: Диагностика на сервере

Перед переносом файлов необходимо определить точное состояние миграций в базе данных на продакшн-сервере.

1. **Подключитесь к серверу** через SSH и перейдите в каталог проекта (backend).
2. **Посмотрите список файлов миграций**, которые сейчас физически находятся на сервере:
   ```bash
   ls backend/app_resumes/migrations/
   ```
3. **Проверьте примененные миграции** в базе данных сервера:
   ```bash
   python manage.py showmigrations app_resumes
   ```
   Найдите **последнюю примененную миграцию** (она отмечена крестиком `[X]`). 
   *Например, предположим, что последней примененной миграцией на сервере является:* `0009_server_custom`

---

## 🔗 Шаг 2: Выстраивание цепочки новых миграций

Чтобы избежать конфликтов, вам нужно переименовать три новые локальные миграции и переписать их зависимости так, чтобы они выполнялись строго **после** последней миграции на сервере.

Наши новые локальные файлы миграций:
- `0008_parentreview_student_resume_student.py`
- `0009_auto_20260525_1630.py` (миграция данных)
- `0010_remove_parentreview_student_crm_id_and_more.py`

### 1. Переименование файлов при переносе
Переименуйте локальные файлы при их копировании на сервер так, чтобы их порядковые номера шли сразу за номером последней серверной миграции.

*Если последняя миграция на сервере имеет префикс `0009`:*
* Переименуйте `0008_parentreview_student_resume_student.py` в **`0010_parentreview_student_resume_student.py`**
* Переименуйте `0009_auto_20260525_1630.py` в **`0011_auto_20260525_1630.py`**
* Переименуйте `0010_remove_parentreview_student_crm_id_and_more.py` в **`0012_remove_parentreview_student_crm_id_and_more.py`**

### 2. Обновление зависимостей в первой новой миграции
Откройте первый перенесенный файл на сервере (который теперь называется `0010_parentreview_student_resume_student.py`).

Найдите список `dependencies`:
```python
dependencies = [
    ('app_resumes', '0007_alter_student_options_student_study_start_date'),
]
```

Измените его так, чтобы он ссылался на **последнюю примененную миграцию на сервере** (в нашем примере — `0009_server_custom`):
```python
dependencies = [
    ('app_resumes', '0009_server_custom'),  # Имя последней примененной миграции на сервере
]
```

### 3. Проверка зависимостей в последующих миграциях
Проверьте, чтобы остальные переименованные файлы миграций ссылались на своих новых предшественников:

1. Откройте `0011_auto_20260525_1630.py` и убедитесь, что зависимость указывает на измененное имя:
   ```python
   dependencies = [
       ('app_resumes', '0010_parentreview_student_resume_student'),
   ]
   ```
2. Откройте `0012_remove_parentreview_student_crm_id_and_more.py` и убедитесь, что зависимость указывает на измененное имя:
   ```python
   dependencies = [
       ('app_resumes', '0011_auto_20260525_1630'),
   ]
   ```

---

## 🚀 Шаг 3: Безопасное применение изменений

После того как последовательность файлов выстроена в цепочку:

1. **Создайте резервную копию базы данных сервера**:
   ```bash
   cp db.sqlite3 db.sqlite3.backup_before_fk
   ```
2. **Примените миграции**:
   ```bash
   python manage.py migrate app_resumes
   ```
3. **Убедитесь в успешном применении**:
   Проверьте, что все миграции отмечены как `[X]`:
   ```bash
   python manage.py showmigrations app_resumes
   ```

Теперь база данных на продакшн-сервере обновлена, связи переведены на внешние ключи (ForeignKey), а кастомная логика переноса данных успешно выполнена поверх вашей существующей серверной схемы.
